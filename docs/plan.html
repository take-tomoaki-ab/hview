背景

Claude Code とのやりとりは、ターミナル上の Markdown テキストが中心です。比較表・処理フロー・画面レイアウトのように「構造」を持つ情報は、テキストのままだと読み手が頭の中で組み立て直す必要があり、確認に時間がかかります。図つきの HTML を見ながら会話できれば、この負荷はかなり下がります。

既に /html スキル（~/.claude/skills/html）があり、会話の話題を 1 枚の HTML にまとめて Chrome で開くことはできます。ただしこれは単発の書き出し操作で、対話のたびに手で叩き直す必要があります。今回ほしいのは、会話を続けている間ずっと「最新の図が横に出ている」状態です。

検討したこと

要件は「アプリ形式は問わない」「マークをつけたら HTML が返り、アプリ内でレンダリング結果を確認できる」「簡単にファイルエクスポートできる」の 3 点で、最重視は「HTML を見ながら AI と対話できる」ことです。この観点で 4 形式を比較しました。

形式対話しながら見られるか実装コスト難点判定
Chrome 拡張 claude.ai の Web UI 内なら可 中 ターミナルの Claude Code と繋がらない。普段の作業導線から外れる 不採用
VS Code 拡張 1 ウィンドウで完結し理想的 大 拡張 API の実装と VSIX 配布が必要。VS Code を使う前提に縛られる 後回し
デスクトップアプリ 可（何でもできる） 特大 ターミナル自体を内包する必要があり、投資に見合わない 不採用
CLI + ローカルビューア ターミナルの横にブラウザを 1 枚置くだけ 小 ウィンドウが 2 つに分かれる 採用

採用案の構成要素は、ローカルサーバ（hview serve）、Claude Code の hooks、スキル、ビューア画面の 4 つです。プロンプト送信からブラウザへの反映までの流れは次のとおりです。

トリガー（マーク）の 3 系統

要件では「スキルでもトグルボタンでもよい」とされているので、使い分けられるよう 3 つ用意します。いずれも最終的には .claude/hview/mode.json の状態に集約され、判定ロジックは 1 箇所で済みます。

系統操作有効範囲向いている場面
インラインマークプロンプト内に #html と書くそのターンのみ普段はテキストで、この 1 回だけ図がほしいとき
スキルトグル/hview on / /hview off解除するまで継続設計検討など、しばらく図を見続けたいとき
ビューアのボタンブラウザ画面右上のトグル解除するまで継続ブラウザを見ている流れのまま切り替えたいとき

hook が注入する指示の要旨

モードが ON のとき、UserPromptSubmit hook が次の内容を追加コンテキストとして渡します。ここが仕組み全体の心臓部です。

  • 回答の実体は単一ファイルの HTML として .claude/hview/<session-id>/turn-<n>.html に Write すること
  • チャット本文には 2〜3 行の要約とファイル名だけを書き、HTML の中身を本文に貼らないこと（トークンの二重消費を避けるため）
  • 比較・フロー・前後差分は図（インライン SVG）にすること。外部 CDN・外部フォント・外部画像は使わないこと
  • ライト / ダーク両対応にすること。既存の ~/.claude/skills/html/assets/template.html を土台にして見た目を揃えること

ディレクトリ構成

.claude/hview/
├── mode.json                 # ON/OFF と出力モード（毎ターン新規 / 同一ファイル更新）
└── <session-id>/
    ├── index.json            # ターン一覧（タイトル・時刻・ファイル名）
    ├── turn-001.html
    └── turn-002.html

ビューア画面

ブラウザ 1 タブに収めます。左にターン履歴、中央にプレビュー、上部に操作系という構成です。

  • 自動更新：WebSocket で通知を受けて差し替えます。スクロール位置は維持します
  • ターン履歴：過去のターンの図に戻れます。「さっきの比較表もう一回見せて」を会話なしで解決できます
  • ピン留め：特定の HTML を固定し、新しいターンが来ても勝手に切り替わらないようにします。これが「見ながら対話する」の要です
  • 出力モードの切替：毎ターン新規ファイル / 同一ファイルを更新、の 2 モード。後者にすると「今の図のここを直して」がそのまま成立します
  • セキュリティ：プレビューは sandbox="allow-scripts"（allow-same-origin は付けない）の iframe に隔離し、CSP で外部通信を止めます

エクスポート

生成物が最初から単一ファイル完結なので、エクスポートは実質「置き場所を選ぶだけ」になります。

  • HTML をそのままダウンロード（自己完結なので受け取った人がオフラインで開ける）
  • ~/Desktop/codes/html-output へ保存（既存 /html スキルの出力先と揃える）
  • 絶対パスをクリップボードへコピー
  • ブラウザの印刷ダイアログ経由で PDF 化

社内共有が必要なときは、保存したファイルを既存の push-to-prototypes スキルに渡せばそのまま静的サイトとして公開できます。

決定事項

決定

CLI + ローカルビューア方式（Bun 製サーバ + Claude Code hooks + ブラウザビューア）で進めます。VS Code 拡張版のフロントエンドは Phase 3 の任意項目として残し、まず作りません。実装はまだ着手しておらず、以下は設計案の確定という意味での決定です。

未決

コードの置き場所（独立リポジトリにするか ~/.claude/tools/ 配下に置くか）と、hook をユーザー設定・プロジェクト設定のどちらに登録するかは未決です。後者は全プロジェクトに影響が及ぶため、決める前に影響範囲の確認が要ります。

根拠

CLI + ローカルビューアを選んだ理由は 3 つです。

  • フロントを選ばない：Claude Code はターミナル・VS Code・デスクトップアプリのどれからでも使えます。hooks とファイル書き出しに乗せておけば、どの入り口からでも同じビューアに反映されます。拡張として作ると、その拡張のホストに縛られます
  • 配布・審査が要らない：Chrome 拡張も VS Code 拡張もパッケージングと配布の手間がかかります。ローカルサーバなら bun で起動するだけで、修正もその場で反映できます
  • 既存資産をそのまま使える：/html スキルのテンプレートと作図ルールがすでに整っており、「単一ファイル完結・外部依存なし・ライト/ダーク対応」という制約も既に守られています。ビューア側で追加のレンダリング処理を持たずに済みます

逆に VS Code 拡張を捨てきらないのは、ウィンドウが 2 つに分かれる点が唯一かつ実害のある欠点だからです。運用してみて画面の行き来が煩わしければ、サーバ側はそのままにビューアだけを Webview として作り直せます。

実装の進め方

  1. Phase 0 — PoC：hview serve でファイルを配信し、ブラウザで手動リロードして表示できるところまで。hooks はまだ繋がず、この方式で本当に読みやすくなるかだけを確かめます
  2. Phase 1 — MVP：hooks 連携（UserPromptSubmit での指示注入 / PostToolUse での通知）、WebSocket による自動更新、HTML ダウンロードと Desktop 保存。ここまでで要件 3 点は満たします
  3. Phase 2 — 対話性の強化：ターン履歴、ピン留め、ビューア上のトグルボタン、同一ファイル更新モード。「見ながら対話する」の質はこの段階で決まります
  4. Phase 3 — 任意：プレビュー内の要素を選んで「ここを直して」と指示を送り返す逆方向フィードバック、VS Code Webview 版のフロントエンド。Phase 2 まで運用してから必要性を判断します
